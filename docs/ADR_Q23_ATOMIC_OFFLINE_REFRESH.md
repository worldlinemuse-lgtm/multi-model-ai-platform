# Q23 — transactional-style staged offline shell refresh

**Decision date:** 2026-10-14. **Scope:** same-origin GitHub Pages app shell, no user data in service-worker CacheStorage.

Existing `REFRESH` called `cache.addAll` directly on the active offline shell. A partial cache failure or competing refresh requests from two tabs could expose a mixture of old/new app modules while offline, and a failed update could be reported without preserving a known complete shell. Installation already protected other worker versions, but manual refresh did not.

**Design:** each service-worker version uses a base shell cache, an application-scoped control cache containing the *active shell pointer*, and two rotating candidate refresh caches. Refresh requests from separate client tabs enter one promise queue within the controlling worker; each fetches and validates all shell assets into the inactive slot. Only after all assets are verified does it atomically update a single pointer Response. Failed addAll or pointer writes delete the candidate slot and do not change the pointer. Offline fetch resolves the active fully staged slot, falling back to the original installed shell. Online remains network-first. During activation, obsolete versions are removed, while the version's control pointer and staging slots are retained. Acknowledgement includes exact number of refreshed assets and cache slot. Partial failure reports an error rather than success. User files, credentials and model prompts are not stored in this cache.

**Security and residual risks:** CacheStorage is best-effort, so browser eviction can remove any cache; stale data or service-worker process restarts cannot be entirely prevented. Network-first may still serve newer HTTP responses when online than the pinned offline snapshot; this is stated rather than hidden. UI tells user to reload after refresh if necessary. The pointer is an internal fixed-origin request; no third-party fetch or arbitrary path injection. The service-worker code uses the existing scope check, no external origin interception. Cache collisions across unrelated repositories are avoided by unchanged deployment scope and dedicated version names; historical cleanup still uses legacy prefix.

No upstream code copied.

**Acceptance:** deterministic Node VM tests for failure on third asset, retry after failure, pointer-write rejection, two concurrent refreshes serializing, complete offline fallback and app-scoped cache cleanup. Real Chromium two controlled-tab acceptance and offline reload, both checkout and public GitHub Pages; hosted file SHA matches GitHub head. No silent downgrade of tests.
